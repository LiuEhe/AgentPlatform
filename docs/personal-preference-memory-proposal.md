- 日期：2026-11-05。

## 1. 目标与范围

首版将个人偏好作为用户明确管理的持久设置：保存后，新会话及已有会话的下一次回答都可以使用；当前消息中的明确要求优先于长期偏好。

建议首版仅支持会话助手普通回答的三个维度：

| 偏好键 | 建议取值 | 作用 |
| --- | --- | --- |
| `answer_language` | `zh-CN`、`en` | 默认回答语言 |
| `answer_detail` | `concise`、`standard`、`detailed` | 默认详细程度 |
| `answer_structure` | `prose`、`bullets` | 默认段落或列表形式 |

未保存某项时使用现有回答策略，不自动补写默认记录。枚举、范围和产品文案均待实施前确认；本方案不保存任意自由文本指令。

首版不包含：从聊天自动归纳偏好、对“记住/忘记”口令进行语义识别、历史会话回填、用户画像与事实库、组织共享规则、历史审核经验、Embedding 和向量检索。

偏好不授予工具调用能力，不改变审核意图、参数、标准或结论。当前完整审核报告由子 Agent 生成并返回，普通回答偏好不自动改变该报告。若要支持报告格式偏好，应另行确认审核 Agent 的契约和作用范围。

## 3. 可选方案与建议

| 方案 | 优点 | 代价与限制 |
| --- | --- | --- |
| A：官方 PostgreSQL Store，显式管理固定偏好 | 复用已有依赖与数据库；读写简单；无需模型抽取和向量服务 | 需要官方 Store 建表、受限适配和管理入口；身份约束由应用保证 |
| B：应用自建偏好表，使用现有业务数据库基类 | 可直接复用业务事务，适合未来需要强关系约束的设置 | 当前需求可以由官方 Store 满足，自建表会重复已有键值能力 |
| C：自动抽取自由文本记忆并语义检索 | 能保存更开放的习惯、事实与经验 | 增加抽取错误、冲突、来源、Embedding 与检索评估成本，超出当前需求 |

建议 A，尚未确认选型。选择官方能力承载键值存取，应用仅实现身份绑定、枚举校验、快照读取和使用策略。B 保留为后续出现具体事务或约束缺口时的替代；C 不纳入首版。

用户已确认的是个人偏好场景，尚未确认独立设置入口、固定枚举或自动提取方式。本方案采用显式设置，是为控制首版范围提出的默认建议。

## 4. 拟议数据模型与生命周期

采用命名空间 `("users", "<可信 user_id>", "preferences")`。每个偏好键对应一条记录，避免修改单项时覆盖其他项。

示例，非已落库数据：

```json
{
  "namespace": ["users", "<user_id>", "preferences"],
  "key": "answer_detail",
  "value": {"value": "concise", "source": "explicit_setting"}
}
```

- 创建、修改和删除均为独立设置操作，不依赖模型配置，也不绑定某轮聊天是否成功。
- 同一键使用 `aput` 更新；重复写入相同取值幂等，不生成多条记忆。
- 不同键独立修改；同一键并发写入按数据库最终写入顺序生效，不承诺浏览器点击顺序。首版不加入版本冲突协议；若产品要求避免同键覆盖，再单独设计。
- 用官方记录的创建、更新时间，不复制一套时间字段；首版不设置 TTL。
- 命名空间不包含登录 session ID，重新登录后仍可读取；默认用于本方案明确接入的会话助手，不自动授予所有 Agent。
- 删除会话不删除用户级偏好；删除偏好不修改历史消息和已经生成的报告。
- 首版没有账号永久删除流程；未来新增时必须把用户偏好纳入清理范围。
- 备份与数据库一起处理，删除在线偏好不宣称清除了既有备份。

## 5. 拟议读写流程

### 5.1 显式管理

1. API 复用现有登录身份与写请求保护，使用服务端解析的用户身份。
2. 应用服务验证固定偏好键和值，绑定该用户命名空间。
3. 基础设施适配调用官方 Store；写入成功后才返回保存成功。
4. 网络响应丢失时，客户端可以重新读取确认；相同取值可以安全重试。

客户端不提交目标 `user_id` 或 namespace。管理员身份不增加读取他人偏好的能力，Agent 与模型均不能指定存储归属。

### 5.2 一次聊天执行

1. 会话服务沿用现有会话归属与执行检查；在任务真正开始执行时，按可信拥有者读取三个已知键，得到有界、只读的本轮快照。
2. 通过 `ConversationTurnResources` 传给适配器，再进入 Agent 的执行上下文。运行时继续透传中立资源，不解释偏好。
3. 意图分类仍使用原有业务上下文。普通回答节点才使用偏好，不能由偏好触发审核、选择材料或补齐业务参数。
4. 上下文准备按本轮偏好的实际序列化开销预留预算；普通回答最终请求再次检查 24000 字符上限，复用现有预算算法。
5. 语言、长度和形式由受控枚举映射为 Agent 提示中的建议；遵守系统约束，本轮明确要求优先。模型遵循程度仍需效果验收。

偏好快照不写入持久消息、摘要或图状态，不作为材料目录内容。已有会话每轮重新读取，不从旧 checkpoint 延续旧偏好。执行中修改或删除偏好不追溯改变本轮快照；下一次执行重新读取。

### 5.3 故障与一致性

- 官方 Store 与业务 asyncpg 事务不宣称原子；首版通过独立设置操作避开“图写成功、聊天归档失败”的跨存储发布问题。
- 读取偏好失败时建议明确报告存储不可用，不静默当作“用户没有偏好”；不得推进本轮成功记忆位置。具体执行前拒绝或运行失败行为由应用用例统一处理，并遵守现有状态机。
- 修改偏好失败时不得返回保存成功；提交结果不明时允许读取核实和幂等重试。
- 不使用长期进程缓存，减少跨会话过期副本和删除失效问题。
- 不引入后台提取、队列、outbox 或补偿调度器；如果将来允许聊天中保存记忆，需要重新设计与成功归档的关系。

`infrastructure/memory/` 是现有 infrastructure 下的拟新增子包，用于跨会话用户记忆，避免把用户偏好存储混入身份仓储或短期会话存储。官方 Store 拟成为继 checkpointer 后的另一项受限 SDK 数据库例外，必须在实施前确认，并同步架构规则；业务 SQL 仍统一使用现有 BaseDatabase。

首版建议独立管理 Store 的 Psycopg 池，不迁移现有 checkpoint 资源。其连接额度需要与业务池、checkpoint 池合计；若均沿用默认上限 5，三个池合计上限为 15。后续计划需核定实际额度、同 schema、Windows Selector loop、关闭顺序以及异常清理，不通过本方案提前修改配置。

## 7. 拟议 HTTP 与前端范围

建议接口，尚未批准或实现，均沿用项目 API 前缀及现有身份保护：

| 方法与路径 | 语义 |
| --- | --- |
| `GET /users/me/preferences` | 返回三个已保存偏好，未保存项为空，不写入默认值 |
| `PUT /users/me/preferences/{key}` | 保存或替换一个受支持取值，返回确认后的偏好 |
| `DELETE /users/me/preferences/{key}` | 删除一个偏好；重复删除成功，后续执行恢复默认策略 |

校验、存储失败和身份失效应复用现有错误体系，正式契约在实施计划阶段对照 [错误码](errors.md) 确认，不在本文宣称已有新错误码。

建议在账号页增加小型偏好设置区；展示已保存值和“使用默认”状态，保存与删除有明确成功或失败反馈。需要遵守现有认证代次与迟到响应丢弃机制。当前只描述功能，不提供或批准视觉设计。

后续验收应覆盖：

- 同一用户保存偏好后，新会话、已有会话下一轮及重新登录后均生效；不同用户互不影响。
- 未设置、覆盖、重复保存、删除和重复删除符合契约；同键并发写入符合已说明语义。
- 普通回答遵循偏好，本轮要求优先；审核意图、参数、完整报告与工具权限不受偏好改变。
- 偏好不进入 checkpoint/摘要；删除后下一轮不从旧持久状态重新注入，执行中的快照边界明确。
- 最终序列化预算包含偏好；无模型配置时仍能管理设置；Store 故障不伪报保存成功或悄悄丢弃偏好。
- 官方 setup、重复 setup、空库初始化失败重试、已有业务库补表和启动无自动建表，均在专用测试 schema 验证。

- HTTP/前端覆盖身份隔离、已有写保护、切换账号清理和迟到响应；真实模型偏好遵循程度单独验收。
