# 开发工作流

## 1. 明确需求

- 用简短任务说明列出目标、验收标准、禁止事项和预期修改范围。
- 区分必须实现的内容与额外建议。遇到需求与现行架构或已接受 ADR 冲突时先报告并等待决定。
- 对复杂或跨模块任务先提供分步计划，说明依赖关系、风险和验证方式；简单局部修改可使用简短清单。

## 2. 检查现状

- 阅读根 `AGENTS.md` 及相关治理文件、README、对应实现、调用方和配置。
- 搜索已有 API、服务、节点、组件、依赖和测试，避免重复实现。
- 用 Git 状态和 diff 确认已有用户修改。不得覆盖或清理与任务无关的工作。
- 记录计划触及的文件；发现需扩大范围时，先解释必要性并取得用户确认。

## 3. 实施修改

- 只完成已确认的需求，按最小必要范围修改。
- 遵循当前目录职责和邻近代码风格；不借机重构无关代码。
- 不擅自新增目录、依赖、数据库结构、架构模式或基础设施。
- 代码、接口、依赖或目录职责变化时，检查需要同步更新的文档。
- 长任务在关键阶段记录已完成内容、剩余工作、验证结果和未解决问题，便于新会话恢复。

## 4. 验证和汇报

- 修改代码后先运行与改动相关的现有检查；新功能或 Bug 修复应提供能覆盖真实业务行为的测试。
- 如果工具、服务或测试数据不可用，明确说明未执行项和原因，不得把未执行描述为通过。
- 查看最终 Git diff，确认没有无关修改、意外密钥、锁文件变化或生成物。
- 汇报分清：已实现、已运行且结果如何、未运行、仍未验收。测试失败需给出失败信息和影响。

## 5. 结束条件

任务满足用户验收标准、相关检查结果已如实报告、文档已同步且未决事项已列明后，才可报告完成。测试通过不等同于用户验收；未执行测试不等同于测试通过。
