# 开发工作流

按“明确目标 → 核对现状 → 修改 → 验证 → 交付”执行。

## 1. 明确目标

写清要解决的问题、验收条件、修改范围和禁止事项。简单任务用短清单；复杂或跨模块任务先给计划，说明顺序、风险和验证方式。额外建议单列。

## 2. 核对现状

阅读 [AGENTS.md](../../AGENTS.md)、相关 README、治理文档、实现、调用方和配置。搜索可复用的模块、官方 API、依赖和测试。

检查 Git 状态及 diff，保留用户已有修改。遇到规则冲突或需要扩大范围时，按[治理流程](governance.md)确认后再继续受影响部分。

## 3. 修改

只做当前范围内的必要改动，遵守职责边界与现有风格，不顺手重构。目录、依赖、数据库、认证等变更按相应审批规则处理；代码或契约变化时同步文档。

前端样式或交互先提供原型截图供用户 review，优先使用 Figma；受限时说明实际工具。用户明确跳过原型时按其指令执行。

## 4. 验证

按[质量门禁](quality-gates.md)选择相关检查。功能或缺陷检查应验证实际行为和边界，不能通过删除测试、降低断言来制造通过结果。纯文档修改检查链接、路径、命令和规则一致性。

检查失败要调查并报告；无法执行时说明原因。完成前查看 diff，排除无关改动、密钥、锁文件和生成物。

## 5. 交付

说明改了什么、检查结果、未检查与未验收事项。测试通过不等于用户验收，未执行不算通过。

默认将改动留在工作区，由用户 review 并提交；未经明确要求，不执行 `git add`、`git commit` 或 `git push`。跨会话任务按[上下文管理](context-management.md)记录进展。
