# 治理原则与变更机制

本文说明哪些改动可以直接做，哪些需要先确认。项目当前实现见[项目目录](project-structure.md)和[架构规则](architecture-rules.md)；这里的治理要求不代表已有自动检查。

## 规则优先级

平台与系统要求 → 用户当前任务 → [AGENTS.md](../../AGENTS.md)及关联治理文档 → 已接受的技术决策记录（ADR）→ README、注释和历史计划。

用户未要求的范围扩展不能由 Agent 自行批准。提议或废弃的 ADR、历史计划只能提供背景，不能当作现状或实施授权。

遇到冲突时，说明冲突、涉及文件和可选处理方式，暂停受影响部分，等待用户决定；决定改变后更新相应记录。

## 什么需要先确认

| 改动 | 要求 |
| --- | --- |
| 已有职责内的局部实现 | 先查现状和调用方，按当前需求实施；必要时可新增局部文件 |
| 新增顶层目录、后端或前端一级模块、跨层抽象、框架、基础设施，或改变公共契约 | 提交问题、目标职责、方案、较小替代方案、影响和计划，由用户确认范围 |
| 依赖、数据库、删除、认证或外部环境操作 | 同时遵守[风险管理](risk-management.md) |
| 额外改进或未来设想 | 单独列为建议，未确认不实施 |

新增或迁移文件应说明职责、输入输出、依赖和实际调用方，以及现有模块为何不适合承载。已明确批准的范围不重复确认。

## 怎样维护决策和文档

影响后续架构、依赖、接口、安全或维护成本的重要决定才需要 ADR，记录背景、决定、状态、日期、后果和依据。小型局部选择无需另写记录。

实现变化时同步相关 README 和治理文档，只更新受影响内容。当前实现与拟变更分开写；正式说明引用源码、部署资产和治理文档，不依赖任务设计或执行记录。自动化要写明命令和入口，未接入的能力标为建议。
