# AgentPlatform 前端框架方案

## 目标与范围

前端是 AgentPlatform 的智能体使用入口，首版聚焦两类页面：智能体主页和智能体工作台。工作台以对话为主，并为有执行步骤的智能体展示工作流进度和结果。

当前仓库使用 Vue 3、TypeScript、Vite 和 pnpm。本方案只定义前端结构与接入边界，不包含后端改动，也不假设尚未实现的接口已经可用。

首版以现有的制度审核智能体为例，优先让用户能够找到智能体、提交 DOCX 制度草稿并查看 Markdown 审核报告。通用对话和实时工作流能力待后端接口具备后接入。

## 页面与路由

| 路由 | 页面 | 职责 |
| --- | --- | --- |
| `/` | 智能体主页 | 展示平台入口和可用智能体卡片；首版展示制度审核智能体。 |
| `/agents/:agentId` | 智能体工作台 | 承载当前智能体的输入、执行反馈和结果；根据智能体能力呈现文件审核或对话交互。 |

智能体主页不是管理后台。首版不包含智能体配置、知识库管理、任务管理、报告中心或用户管理页面。

### 工作台区域

- **标题与说明**：显示智能体名称、用途和支持的输入类型。
- **输入区**：制度审核先提供 `.docx` 文件选择和提交；后续对话型智能体可提供消息输入框。
- **执行反馈**：显示准备中、执行中、成功或失败状态。后端尚无流式进度接口时，首版只显示请求级状态，不模拟节点进度。
- **结果区**：制度审核结果以 Markdown 报告呈现；对话和工作流结果接入后端相应数据结构后再扩展。

## 前端模块边界

页面负责组合功能，不直接编写 HTTP 请求或承载可复用的业务展示逻辑。API 模块负责后端通信；类型定义描述前后端交换的数据；通用组件不绑定某一个智能体的业务规则。

建议目录如下，按功能逐步添加，不要求一次创建所有空目录：

```text
src/
├── app/                    # 应用入口级配置
├── router/                 # 路由表与导航守卫（需要时）
├── views/
│   ├── AgentHomeView.vue   # 智能体主页
│   └── AgentWorkbenchView.vue # 智能体工作台
├── components/
│   ├── agents/             # 智能体卡片、信息头等
│   ├── workbench/          # 输入区、执行状态、结果区
│   └── common/             # 跨页面通用展示组件
├── features/
│   └── institution-review/ # 制度审核专属输入、结果与类型
├── api/                    # HTTP 客户端与接口封装
├── types/                  # 跨功能共享的数据类型
├── composables/            # 可复用交互状态与逻辑
└── assets/                 # 静态资源
```

具体约定：

- `views/` 只负责页面级布局和功能组合。
- `features/` 放智能体特有的输入流程、结果呈现和相关类型，避免把业务判断堆进通用组件。
- `api/` 集中处理 API 前缀、请求、错误转换和超时等通信细节。组件不得直接调用 `fetch`。
- `components/common/` 只收纳至少被两个场景复用的组件；避免为未来需求预先搭建组件库。
- `composables/` 用于跨组件复用的前端行为，不代替 API 层或业务功能模块。
- 暂不加入全局状态管理。页面局部状态先使用 Vue Composition API；出现跨路由共享且复杂的状态后再评估 Pinia。

## 技术选择

- **Vue 3 + TypeScript + Vite**：沿用现有脚手架和单文件组件模式。
- **Vue Router**：页面已有主页与工作台两个稳定入口，采用路由明确表达页面导航。
- **Markdown 渲染**：审核报告为 Markdown。渲染实现应对不可信内容做安全处理；确认依赖和策略后再接入具体库。
- **HTTP 客户端**：首版可用浏览器 `fetch` 封装轻量 API 层；当拦截器、取消、重试等需求实际出现时再评估额外依赖。
- **状态管理**：首版不新增 Pinia 等全局状态依赖。

## API 接入现状

当前后端文档提供以下接口：

| 接口 | 用途 | 前端使用方式 |
| --- | --- | --- |
| `GET /health/live` | 检查服务进程状态 | 可用于开发期间诊断服务连通性，不作为智能体主页内容。 |
| `GET /health/ready` | 检查模型及 RAGFlow 配置状态 | 可用于提示服务是否准备就绪；具体响应结构以实际 API schema 为准。 |
| `POST /api/v1/reviews` | 上传 `.docx` 并同步返回 `text/markdown` 审核报告 | 使用 `FormData` 发送文件；成功后展示报告，失败时显示可理解的错误信息。 |

审核请求暂不持久化报告，也没有后端任务记录或节点级进度。因此刷新页面后不承诺恢复执行历史；请求期间的“执行中”状态由前端本地维护。

后端目前没有智能体目录、通用会话、消息流式输出或工作流节点事件接口。实现通用聊天前，需由后端明确会话标识、消息格式、流式协议、停止执行和错误格式；前端不应自行假设这些契约。

## 交互状态与错误处理

制度审核流程至少区分以下状态：

1. **空闲**：等待用户选择 DOCX 文件。
2. **校验失败**：文件扩展名不支持或文件为空时，在提交前提示。
3. **提交中**：锁定重复提交入口，并显示正在审核。
4. **成功**：展示 Markdown 报告。
5. **失败**：保留用户已选文件，展示可读错误并提供重试入口。

前端可依据当前后端行为处理 `415` 不支持的文件类型、`413` 文件过大和 `503` 服务未就绪等响应。具体错误响应格式须以 `backend/app/core/errors.py` 和实际接口行为为准；API 层应把服务响应转换为统一的前端错误对象，页面避免直接解析底层异常。

如果未来工作流接口提供事件流，执行步骤、阶段状态与最终结果由 API/功能层映射为工作台视图状态；展示组件只消费前端定义的状态类型，不依赖 LangGraph 等后端实现细节。

## 配置与开发

- API 地址通过 Vite 环境变量配置，例如 `VITE_API_BASE_URL`；开发环境可由 Vite 代理转发到后端。
- 环境变量只存放公开的前端配置。模型密钥、RAGFlow 密钥等服务端凭据不得写入前端。
- 使用仓库约定的 pnpm 安装依赖和运行脚本；当前脚手架脚本为 `dev`、`build` 和 `preview`。
- 后端本地启动与环境准备见仓库根目录及 `backend/README.md`。

## 实施顺序

1. 建立主页和工作台路由及最小页面骨架。
2. 展示制度审核智能体入口，打通 DOCX 上传、请求状态、错误提示和 Markdown 结果展示。
3. 根据真实使用反馈调整通用组件与功能模块边界。
4. 待后端定义会话和工作流事件契约后，再扩展对话输入、流式消息、节点进度和历史恢复。

每一步都以已有接口和可验证的用户流程为依据，避免为尚未确定的能力提前建设复杂状态层或抽象框架。
